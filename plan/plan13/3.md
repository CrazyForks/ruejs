# Phase 3: 扩展 design 与 site 页面覆盖

Phase 3 负责把 [app/pages/design](../../app/pages/design) 与 [app/pages/site](../../app/pages/site) 的关键页面补进回归矩阵。前者主要覆盖 design 组件与 runtime 交互，后者主要覆盖路由、文档加载、markdown 注入和导航边界。

## 目标

1. design 目录里所有带交互状态的示例页面，至少各有一条页面主流程测试。
2. site 目录里所有 route/fetch/markdown/nav 相关页面，至少有一条真实主流程测试。
3. 让 design/site 相关删除动作不再只能靠手点页面验证。

## 建议优先级

1. design：在现有 [tabs.actual.spec.tsx](../../packages/runtime/__tests__/tabs.actual.spec.tsx) 基础上，优先补 Accordion、Collapse、Menu、Dock、Countdown、HoverGallery。
2. site：在现有 [guideDocDetail.actual.spec.tsx](../../packages/runtime/__tests__/guideDocDetail.actual.spec.tsx) 基础上，继续补 PageDocDetail、ApiDocDetail、DocsIndex、SiteHome 与 persistent sidebar 相关页面。
3. 对只展示静态文案而不触发 runtime 行为的 design/site 页面，优先级低于会走 route、watch、fetch、slot、Teleport、shared mount 的页面。

## 工作内容

1. design 页面重点断言组件切换、active 状态、显隐和受控 props 变化。
2. site 页面重点断言 route 参数驱动、fetch 路径、markdown HTML 注入、上一页/下一页导航和共享 sidebar 挂载行为。
3. 若站点外围布局过重，优先 mock 掉与当前测试目标无关的外壳，但保留页面核心协议。
4. 对 markdown 页面的测试，优先覆盖“加载成功 / 未找到 / 加载失败”三类状态，而不是只测 happy path。

## 风险

- site 页面容易把文档内容、布局外壳和 runtime 主流程混在一起，导致测试关注点失焦。
- design 页面若只断言文案而不看状态切换，测试价值会很低，无法为删除动作提供真正护栏。

## 完成标准

1. design 目录的状态型示例页面已具备最小主流程测试。
2. site 目录的文档详情与导航主路径已具备最小主流程测试。
3. 与 design/site 相关的 runtime 删除动作都能找到明确页面护栏。
