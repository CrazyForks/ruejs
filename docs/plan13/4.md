# Phase 4: 以测试门禁驱动安全删除与清场

Phase 4 不再新增测试方向，而是把前面形成的页面矩阵真正绑定到后续删除动作上。删除不再是独立动作，而是“测试准备完成后的一个子步骤”。

## 目标

1. 把页面测试矩阵变成每个删除切片的准入条件。
2. 用窄范围页面回归保护 runtime / router / JSX runtime / site 文档加载相关代码清理。
3. 把这套工作流沉淀成默认执行顺序，而不是一次性救火方案。

## 删除执行顺序

1. 先选一个具体删除切片，例如某个 compat helper、旧 transport 分支、旧 mounted handle 协议或文档加载兜底路径。
2. 明确该切片会影响哪些页面主流程，并先为这些页面补测试或增强断言。
3. 先跑新增页面测试，确认它们能在当前实现下通过。
4. 再做代码删除，并只跑与该切片直接相关的窄范围页面矩阵。
5. 如果窄范围页面矩阵通过，再决定是否继续扩删除范围或补下一批测试。

## 建议门禁

1. 每个删除 PR 至少列出“影响页面 -> 对应测试文件 -> 已执行命令”三项。
2. 页面测试命名继续沿用 `*.actual.spec.tsx` 风格，明确这些用例针对真实页面主流程，而不是低层 helper。
3. 对新出现的页面回归 bug，优先补到 [packages/runtime/**tests**](../../packages/runtime/__tests__)，而不是只在浏览器里手验后继续删除。
4. 当某个页面测试稳定性不足时，先修测试入口或断言粒度，不要绕过它继续删代码。

## 完成标准

1. 后续代码删除已明确依赖页面矩阵，不再跳过测试准备阶段。
2. 页面回归用例已经能作为删除动作的第一道安全门。
3. 计划结束时，主流程 bug 的发现方式应从“删完后浏览器里发现”转成“删之前测试就先卡住”。
