# Phase 3: 迁移 compiler、router 与仓内消费者

删掉 public VDOM 契约之后，仓内依赖这些契约的消费者必须跟着迁移，否则 plan 只会停留在 runtime 自身。Phase 3 的目标是把 compiler、router、custom-elements、app fixtures/examples 一并切到新 contract。

## 当前信号

- [packages/router/src/index.ts](../../packages/router/src/index.ts) 里的 `RouterView` / `createRouteComponentBlock` 仍通过 `h(component, { params }) as any`、`renderAnchor`、`renderBetween` 组合旧 contract。
- [packages/swc-plugin-rue/src/element_slot.rs](../../packages/swc-plugin-rue/src/element_slot.rs) 的注释仍明确说“把原始 slot / children 值交给 renderAnchor，由 runtime 的 Renderable/compat 边界统一处理”。这说明 compiler 输出仍依赖旧 runtime 公开面兜底。
- [packages/swc-plugin-rue/src/element_component.rs](../../packages/swc-plugin-rue/src/element_component.rs) 仍把 component children / slot value 改写成依赖 `renderAnchor` 的输出，说明 compiler 还把 runtime 当默认清洗层。
- [packages/runtime/src/custom-elements.ts](../../packages/runtime/src/custom-elements.ts)、[packages/runtime/src/hooks/useComponent.ts](../../packages/runtime/src/hooks/useComponent.ts) 与 [packages/runtime/src/hooks/useApp.ts](../../packages/runtime/src/hooks/useApp.ts) 仍有基于旧 create/render 公开面的仓内消费。
- app、fixtures、docs/examples 里仍会把 `renderAnchor`、`h`、旧 JSX 口径当成可用 contract。

## 目标

1. 让 compiler 输出只依赖新的 vapor-only / renderable-only runtime contract。
2. 让 router、custom-elements、hooks、app fixtures/examples 不再依赖 `h(...) as any` 或旧 mount-handle 语义。
3. 明确 compiler 的 slot / children output contract，不能继续假设 `renderAnchor` 会兜底清洗旧 shape。
4. 明确仓内哪些消费者要改写成 block/renderable，哪些应直接转为编译产物依赖，而不是运行时 VDOM 依赖。

## 工作内容

1. 先冻结 compiler 输出契约。
   先定义 swc/vite transform 的 slot / children / component output contract，再调整 [packages/swc-plugin-rue/src/element_slot.rs](../../packages/swc-plugin-rue/src/element_slot.rs) 与 [packages/swc-plugin-rue/src/element_component.rs](../../packages/swc-plugin-rue/src/element_component.rs)，让编译输出不再依赖 `h`、旧 jsx-runtime、或“renderAnchor 会帮我接受 compat child shape”这一前提。
2. router 迁移。
   重写 [packages/router/src/index.ts](../../packages/router/src/index.ts) 中 `RouterView` / `RouterLink` / route block 创建逻辑，让它们只依赖 Phase 2 定下的新 renderable/block contract。
3. custom-elements 与 hooks 迁移。
   处理 [packages/runtime/src/custom-elements.ts](../../packages/runtime/src/custom-elements.ts)、[packages/runtime/src/hooks/useComponent.ts](../../packages/runtime/src/hooks/useComponent.ts)、[packages/runtime/src/hooks/useApp.ts](../../packages/runtime/src/hooks/useApp.ts)，把依赖旧 create/render 公开面的地方都拉到新口径，并补齐多源挂载场景的 lifecycle/cleanup 语义。
4. 仓内页面与示例迁移。
   处理 app、fixtures、examples、docs pages，把依赖旧 create/render 公开面的地方都拉到新口径。
5. 测试与 fixture 迁移。
   更新 compiler、router、runtime consumers 的测试，不再以 VDOM/mount-handle 作为默认对照面，并补一组 router/custom-elements/useComponent 的组合型 regression。

## 工作量判断

- 规模：Medium-Large
- 预估：约 5 到 7 个工作日
- 原因：代码量未必比 Phase 2 多，但这里涉及跨包联动；一旦 public contract 改了，仓内消费者都需要同步迁移，测试也会连锁变化。

## 依赖与风险

- 强依赖 Phase 2 先给出稳定的新 public contract。
- 风险点主要在 RouterView、slot/compiler output、custom-elements、useComponent 这些“不是纯 runtime，也不是纯 compiler”的中间层。
- 如果 Phase 2 对 `h/createElement/jsx-runtime` 的处理方案迟迟不定，这一阶段会反复返工。

## 完成标准

1. [packages/router/src/index.ts](../../packages/router/src/index.ts) 不再依赖旧 `h(...) as any` 或 mount-handle 兜底语义。
2. compiler 输出不再把 runtime 的 compat/renderable 边界当成默认清洗层，slot / children contract 已经稳定。
3. [packages/runtime/src/custom-elements.ts](../../packages/runtime/src/custom-elements.ts)、[packages/runtime/src/hooks/useComponent.ts](../../packages/runtime/src/hooks/useComponent.ts)、[packages/runtime/src/hooks/useApp.ts](../../packages/runtime/src/hooks/useApp.ts) 已经迁到新 contract。
4. 仓内 app、fixtures、examples 都已迁到新 contract，并具备稳定测试口径。
