# Wasm 速度构建档位计划

目标：用一次可撤回的 A/B 实验确认 `opt-level=3` 与 `wasm-opt -O4` 能否改善 Rue 热路径，并量化体积代价。

范围：只调整 `runtime-vapor` 的 release 优化参数，复用响应式图基准、运行时体积审计和列表性能用例记录前后数据；达不到门槛时恢复原参数。

范围外：不改 Rust/TypeScript 业务逻辑，不改公开 API，不发布 npm 包，不修改 js-framework-benchmark 实现，也不同时引入共享 effect 优化。

假设：当前 release 明确使用 `opt-level = "z"` 和 `wasm-opt -Oz`；相同工作树、相同机器上的连续 A/B 能判断该构建参数是否值得保留。

## 设计决策

- 只比较当前 `z/-Oz` 与候选 `3/-O4`，不新增长期构建档位或特性开关。
- 候选需让热路径中位数有可复现收益，且 Brotli 体积增长不超过 15%；否则恢复原配置。
- 与其他性能计划串行执行，避免生成的 Wasm 包和机器负载污染结果。

## 架构说明

- 配置入口是 `packages/runtime-vapor/Cargo.toml`，构建仍走现有 `wasm-pack` 脚本。
- 先完成现有渲染调试计划的剩余联合回归，再做本实验；实验期间不改调度模式和测试数据。

## 开发策略

- 本任务是构建参数实验，不适用失败测试；以固定命令、交替运行和产物哈希作为验证。
- 先记录基线，再改一组参数，最后用同一命令复测。
- 只保留通过预设速度/体积门槛的配置。
- 不把本地 A/B 称为已发布版本成绩。
