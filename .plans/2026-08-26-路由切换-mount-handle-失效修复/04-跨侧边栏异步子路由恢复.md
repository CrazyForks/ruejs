## 上下文

- 应用端 `routeComponent` 在客户端使用 `useComponent`，这是既有业务契约，不能改成另一套路由组件协议规避。
- RouterView 在根记录外包裹 depth Provider，布局内部的 RouterView 渲染叶子记录。
- 延迟 anchor remount 必须在创建 handle 的 runtime 中重放，不能在微任务执行时借用当前全局 runtime。
- route key 变化时必须先同步替换旧 child tree，避免旧嵌套 RouterView 在延迟 remount 前继续响应同一次 route signal，并把新 RouterView 错绑到更深的 context owner。

## 测试计划

- 行为：从首页进入嵌套 Examples 懒叶子，再进入嵌套 Guide 懒叶子并往返，每次侧边栏和叶子内容都同时存在。
- 失败验证测试：`restores async leaf content while switching across real sidebar route layouts`。
- 失败验证命令：`pnpm exec vitest run packages/runtime/__tests__/routerView.renderable.spec.tsx -t "restores async leaf content while switching across real sidebar route layouts" --reporter=dot`
- 预期失败原因：延迟 remount 在错误 runtime 中重放 Vapor handle；跨布局时旧嵌套 RouterView 又会在父 route key 替换前消费新路由状态。
- 通过验证命令：`pnpm exec vitest run packages/runtime/__tests__/routerView.renderable.spec.tsx packages/runtime/__tests__/runtimeVapor.js-component-parity.spec.ts --reporter=dot`
- 模拟策略：一组测试使用真实 RouterView、真实侧边栏布局、真实 `useComponent` 懒加载和 memory history；另一组显式切换 active runtime，并断言 keyed child tree 同步替换。

## 完成

- 根因：`commitPendingRender` 脱离所属 runtime 后调用 repeatable factory，新 handle 被注册到默认 runtime，随后交回旧 runtime 渲染而触发 stale handle；跨布局父 remount 延迟时，旧子 RouterView 还会先处理新 route signal，造成新视图 depth/context 错位并留下空锚点。
- 实现：`rue.ts` 与 `vapor-runtime.ts` 都通过 `runWithRuntime(pending.runtime, ...)` 提交；route key 变化进入同步 remount，同 key列表/控件仍走微任务合并。
- 聚焦验证：5 个相关文件共 `100 passed | 1 skipped`，覆盖 runtime parity、真实 RouterView、复杂列表、TreeSelect、Dropdown。
- 全量验证：`pnpm run check` 退出码 0；`npm run test` 为 `391 passed`、`1913 passed | 1 expected fail | 6 skipped`。
- 浏览器验证：真实 Chrome 连续两轮 `/` → `/examples/hello-world` → `/guide/guide/quick-start`，每页正文可见，`pageerror = 0`，无 Rue runtime console error。
