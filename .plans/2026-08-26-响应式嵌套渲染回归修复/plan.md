# 响应式嵌套渲染回归修复计划

目标：修复同步调度下嵌套组件渲染触发的重复刷新、受控状态回写失效和渲染期状态写入泄漏。

范围：聚焦 `runtime-vapor` 的 effect 活动栈与同步重入调度语义，以及 Input Password、Transfer 现有失败用例所覆盖的集成行为；保留工作区已有底层改动，不修改断言或增加跳过逻辑。

范围外：不重构 rue-design 组件视觉结构，不调整公开 API，不处理与本次三处失败无关的模块。

假设：三处失败都在当前 runtime-vapor 调度改动后稳定复现；现有 Input 和 Transfer 测试已经提供真实 DOM 行为的失败基线，底层嵌套 effect 测试用于锁定调度不变量。

## 设计决策

- 优先修复响应式调度的共同原因；只有证据证明组件违反既定渲染契约时，才做局部组件修正。
- 同步模式必须阻止活动 effect 或其活动祖先同步重入，同时不得把同一次状态变化放大为额外渲染。
- 渲染期组件回调不得提交选择状态，也不得把预期的防护行为上报成未捕获运行时错误。

## 架构说明

- Signal 写入统一经过 `schedule_effect_run`；`run_effect_body` 负责维护依赖收集和活动 effect 上下文。
- Transfer 用独立托管宿主渲染左右面板，并通过 `activeManagedRenderRef` 隔离自定义渲染回调中的状态写入。

## 开发策略

- 对会改变行为的代码，使用失败验证-通过验证-重构。
- 在实施步骤前规划失败验证命令和预期失败。
- 将实施步骤限制在失败测试所证明的行为范围内。
- 测试真实行为，不验证模拟对象或实现细节。
