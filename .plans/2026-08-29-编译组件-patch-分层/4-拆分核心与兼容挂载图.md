## 上下文

- 核心 mount 保留 text、Vapor setup/owner、component identity、root replacement、anchor/range 与 cleanup；compat adapter 提供 Element/Fragment 初始挂载和同 tag/key props/children patch。
- `create-rue-base.ts` 应通过静态注入的 mount controller 组装 runtime；不得让核心文件反向 import compat，也不得用运行时 flag 让 bundler 被迫保留两边。
- 完整 `index` 使用 compat factory；`vapor` 使用 core factory。若 core 收到 Element/Fragment handle，应给出明确兼容入口错误，不能静默替换或错误挂载。

## 测试计划

- 行为：vapor/编译消费端 moduleIds 不含 `mount-compat`，仍支持编译组件更新、动态分支和锚点；完整入口继续通过全部 h/Element/Fragment parity；不支持的混用有确定错误。
- 失败验证测试：先在 architecture/tree-shaking 中断言静态依赖方向和消费端 moduleIds，并在 entry-switch 测试增加 core/compat 正反例。
- 失败验证命令：`pnpm exec vitest run scripts/__tests__/runtime-architecture.spec.ts scripts/__tests__/runtime-tree-shaking.spec.ts packages/runtime/__tests__/runtimeVapor.js-vapor-entry-switch.spec.ts`
- 预期失败原因：当前两个入口共用 `runtime-entry.ts -> create-rue.ts -> mount.ts`，因此 Vapor 图必然包含通用 Element/Fragment patch。
- 通过验证命令：`pnpm exec vitest run scripts/__tests__/runtime-architecture.spec.ts scripts/__tests__/runtime-tree-shaking.spec.ts packages/runtime/__tests__/runtimeVapor.js-vapor-entry-switch.spec.ts packages/runtime/__tests__/runtimeVapor.js-public-api-parity.spec.ts`
- 模拟策略：使用真实发布入口 Vite bundle 和真实 jsdom runtime，不 mock resolver 或 tree-shaking。

## 步骤

1. 先加入口模块图、依赖方向、core 正例与不支持输入反例，运行失败验证。
2. 将 `mount.ts` 收敛为 controller factory 与核心分支，把 Element/Fragment 递归逻辑移到 `mount-compat.ts`。
3. 抽出无渲染策略依赖的 `create-rue-base.ts`，由 full/core 两个薄工厂静态注入不同 controller。
4. 让 `runtime-entry.ts` 接受入口提供的 createRue factory；index/vapor 分别导入 full/core，避免共享模块静态引用 compat。
5. 构建并检查产物 moduleIds、错误文案、full parity 和编译组件测试。
